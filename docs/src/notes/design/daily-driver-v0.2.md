# v0.2「日常使い版」の合格基準と作業計画

## 定義

1日の作業を `EDITOR=loom` で loom だけで終えられ、事故が起きても作業を失わないこと。
下の領域すべてで未達が 0 になり、末尾の「v0.2 の合格ゲート」（v0.2 実行計画書1章の7条件）をすべて満たしたとき、作者が v0.2.0 のタグを付ける（D21）。
見た目と発見しやすさの改善（[roadmap-v0.3-v0.5.md](roadmap-v0.3-v0.5.md)）はこの基準に含めない。

## 1日のシナリオ（受け入れ用の通し E2E）

作者の日常を、前夜と、続く12場面に並べたもの（v0.2 実行計画書7章）。v0.1.0 では12場面のうち8場面で止まる。
T9 で、これを1本の PTY シナリオにして `t/e2e/scenarios/` に置く（新しい導線規則 **R9「1日」**）。
同じ scratch の HOME で、複数の loom のプロセスを順に起動し、場面ごとに画面とファイルのバイト列を観測する。

- 台帳とハーネスが `:r9` を受け付けるようにし、固定導線 `r9:daily` を足す。
- 制限時間は R9 だけに設ける。値は両 OS で5回測った最大値の2倍とし、測った値を `docs/src/notes/verification-ledger.md` に記録する。ほかのシナリオの10秒は変えない。

| 時刻 | 場面 | 操作 | 観測 | v0.1.0 | タスク |
|---|---|---|---|---|---|
| 前夜 | 編集中に落ちる | `loom a.lisp` を起動して編集し、保存せずに SIGHUP を送る | exit 129。退避の本文とメタがある | 本文だけが書かれ、メタがない | WP1 |
| 09:00 | 前回の続きから始める | `loom` を引数なしで起動し、案内を確かめてから `M-x list-recoverable-files`、RET、`r`、`C-x C-s` | 案内の文字列。保存後の `a.lisp` が退避の内容と一致する。退避が消えている | 昨夜の SIGHUP で退避した変更が見つからない | WP1 |
| 09:05 | ファイルを探して開く | `C-x p f` | 画面に本文が出る | 通る | なし |
| 09:10 | Lisp を書く | `.lisp` で `RET` `TAB` `M-;` `C-→` | バイト列 | 通る | なし |
| 09:15 | 長い docstring と `#\| \|#` を書く | 3行の docstring と `#\| \|#` を書く | `cell_attrs` | 2行目以降の色が崩れる | WP6 |
| 09:20 | 字下げ先頭へ・空白を詰める | `M-m` `M-\` | カーソルとバイト列 | 何も起きない | WP5a |
| 09:30 | 式を試す | `M-:` に `(loop)`、続けて `C-g` | `Evaluation interrupted`。バイト列が変わらない | ループする式でエディタごと止まる | WP2 |
| 10:00 | ツリーで深い階層を開く | 200項目のディレクトリで `C-x d`、`C-c n` を連打 | 選択行が毎回画面内にある | 選択が画面外に消える | WP3 |
| 10:30 | TypeScript で補完と定義ジャンプ | 実物の typescript-language-server で `M-x lsp-start`、`C-M-i`、`M-.` | 候補が出る。定義へ移る。すべての要求に応答している | サーバによっては初期化の途中で止まる | WP7 |
| 11:00 | 開いているバッファを見渡す | `C-x C-b` | `*Buffer List*` の行 | 未割り当て | WP4a |
| 14:00 | コミットメッセージを書く | `EDITOR=loom git commit` でメッセージを書き、保存して終了 | コミットができている | 通る | なし |
| 15:00 | 置換して確認する | `M-%` で `y` `n` `!` | バイト列 | 通る | なし |
| 18:00 | まとめて保存して終える | `C-x s` で `!`、続けて `C-x C-c` | 全ファイルが保存されている。exit 0 | `C-x s` がない | WP4b |

10:30 は擬似サーバだけでなく、実物の typescript-language-server で確かめる（FR-V04、D16）。
nixd は、WP7 で既存の実物の補完シナリオに「サーバからのすべての要求に、同じ ID の応答が1回ずつ返った」ことの assert を足して確かめる。

- 「すぐ」のタスクは同時に始められる。nix の lock と CI の取り合いで遅くなる場合は、後続の多いタスクから C1、F1、K1、K2、K3、K4、P1、P2 の順に回す。

- 各レーンは `wp/<task>` の bookmark を push して CI を流す。loom の main への着地は作者が行う（D7）。

WP の規模は S < M の相対値で、WP0・WP3・WP5a・WP5b が S、ほかの WP は M。

## v0.2 の合格ゲート

作者は、次をすべて満たしたときに v0.2.0 のタグを付ける（v0.2 実行計画書1章）。

1. 上の表のすべてのタスクが main に着地している。キットはリリースのタグも出ている。
2. Linux と aarch64-darwin の CI で、次がすべて緑。
   - `nix flake check`（全件のテストと境界テストを含む）
   - `nix run .#e2e -- --require-path-coverage`（`missing_paths` が 0）
   - ベンチマークゲート（WP6 で足すケースを含む）
3. どの `boundary-allowlist.lisp` にも、増えた項目がない。
4. 1日のシナリオ（R9）の、前夜と続く12場面がすべて通る。
5. `docs/src/notes/daily-driver-checklist.md` の5行を作者が記入し、Fail がない。Fail があった行は、新しい WP として片付けてある（D22）。
6. 既知の制約（v0.2 実行計画書11章）が、`docs/src/notes/release-v0.2.0.md` に書かれている。
7. タグを付けたときの `release.yml` が成功する。
